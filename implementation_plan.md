# Implementation Plan: EAS + OTA Update Infrastructure for JNTUA Attendance

## [Overview]

Integrate `expo-updates` with a production + staging dual-channel EAS Update workflow so that scraper-script changes and minor UI tweaks reach users over-the-air without a store reinstall or native rebuild.

This plan is grounded in the current reality of the codebase: the entire scraping logic lives in `utils/automationScripts.ts` as pure JavaScript strings injected into the portal WebView, and the entire UI lives in `app/index.tsx`. Both are **pure JavaScript/TypeScript** bundled into the JS runtime, which makes them ideal candidates for OTA delivery through `expo-updates`. Because the app hardcodes the portal URL and relies on DOM selectors that can change whenever the university updates its site, the ability to ship a corrected scraper immediately—without forcing a user to wait for a Play Store review cycle—is the core value proposition of this work.

The approach uses **pure EAS Update** (no remote-code execution, no backend dependency). Two channels provide a safe rollout path: publish to `staging`, validate, then promote to `production`. The app will be configured to fetch and apply updates on launch and on foreground, with a lightweight, non-blocking "checking for updates" indicator so the user experience remains smooth. The configuration is centralized in `app.json`, the update handling is isolated in a small typed module, and all CLI publishing work is automated via npm scripts. This keeps the change minimal, modular, SDK-54-compatible, and production-ready, while respecting the project's mandatory lint gate and anti-over-engineering principles.

The plan deliberately avoids introducing a remote-config backend or executing server-fetched code, prioritizes maintainability through a single update-handler module and a versioned `app.json` updates block, and structures the rollout so that a broken scraper is never silently pushed to every user.

## [Types]

The type-system changes are minimal and isolated to the update-handling module.

- **`UpdateStatus`** (new union type, `utils/updateManager.ts`): represents the lifecycle state of an OTA update check.
  - `"checking"` — an update check is in flight.
  - `"applying"` — a downloaded update is being applied.
  - `"ready"` — an update is available and ready to apply.
  - `"upToDate"` — the app is already on the latest update.
  - `"error"` — an update check failed (network, server, or config errors).
  - `"unknown"` — status could not be determined.

- **`UpdateManager`** (new typed object, `utils/updateManager.ts`): a small single-responsibility bundle exposing the update lifecycle and React state.
  - `status: UpdateStatus` — current update state.
  - `checkForUpdate(): Promise<void>` — triggers an update check and handles the apply/rollback flow.
  - `lastError: string | null` — human-readable message when `status` is `"error"`.

- **`UpdateStatus` variant of `AppState`** (in `app/index.tsx`): the existing `AppState` interface gains a single optional field to surface update status in the UI without restructuring the reducer.
  - `updateStatus: UpdateStatus` — added to hold the value returned by the update manager.

No changes are made to the existing `StudentInfo`, `SubjectAttendanceData`, `AttendanceRecord`, or `MessagePayload` types in `utils/automationScripts.ts`; those are deliberately left untouched to keep the scraper logic stable and independent of the update infrastructure.

## [Functions]

### utils/updateManager.ts (new file)

- **`useUpdateManager(): UpdateManager`**
  - Path: `utils/updateManager.ts`
  - Purpose: React hook that wraps the `expo-updates` API into the typed `UpdateStatus` state machine. Returns `{ status, checkForUpdate, lastError }`.
  - Behavior:
    - On first call, registers a `Updates.addListener` for download/apply events.
    - `checkForUpdate()` sets `status = "checking"`, calls `Updates.checkForUpdateAsync()`.
    - If an update is available: `Updates.fetchUpdateAsync()` → `status = "applying"` → `Updates.reloadAsync()`.
    - If no update: `status = "upToDate"`.
    - On failure: `status = "error"` and store a readable `lastError`. The app continues running on the current bundle (fail-safe).

- **`shouldCheckOnMount(): boolean`**
  - Path: `utils/updateManager.ts`
  - Purpose: Deterministic guard to avoid redundant update checks on every hot reload / re-mount during development. Returns `false` in `__DEV__` and in Expo Go (where `expo-updates` is unavailable), `true` in production builds.

### app/index.tsx (modified)

- **`Index` component** — add `const update = useUpdateManager();` and a `useEffect` that calls `update.checkForUpdate()` once on mount (guarded by `shouldCheckOnMount`). Render a minimal non-blocking banner when `update.status === "checking"` or `"applying"`.

No functions are removed; the existing `appReducer`, `handleNavigationStateChange`, `handleMessage`, and `handleFullReset` remain unchanged.

## [Dependencies]

- **New dependency:** `expo-updates` — installed via `npx expo install expo-updates` to guarantee Expo SDK 54 compatibility (per AGENTS.md rule forbidding `@latest` and requiring the Expo resolution utility).
- **New dev tooling:** `eas-cli` — already installed by the user; will be verified with `eas-cli --version`.
- **No version bumps** to existing core framework dependencies (Expo SDK 54, React Native 0.81.5, React 19.1.0, TypeScript 5.9.2, react-native-webview 13.15.0) — all pinned and left untouched.
- **Integration requirements:**
  - `expo-updates` requires the `updates` block in `app.json` and a `runtimeVersion`.
  - The `eas.json` build profiles must map channels (`preview` → `staging`, `production` → `production`).
  - The user's existing Expo account is used for the cloud build/update service; no self-hosted server is needed.

## [Testing]

The update handling is tested via the project's single mandatory quality gate plus manual verification of the OTA lifecycle.

- **Automatic:** `npm run lint` (expo lint) must pass with 0 errors after all changes — per AGENTS.md, this is non-negotiable.
- **Type validation:** `npx tsc --noEmit` to confirm strict TypeScript compliance introduced by the new module.
- **Manual / build verification:**
  1. Publish a `staging` update and confirm it loads on a staging build.
  2. Publish a `production` update and confirm production users receive it automatically on next launch.
  3. Simulate a failure path (e.g., temporarily break the update URL) to confirm the app falls back to the current bundle without crashing.
  4. Confirm the "checking for updates" indicator appears briefly and disappears without blocking the dashboard.

## [Implementation Order]

The sequencing below minimizes conflicts, keeps the app runnable at every step, and respects the lint gate.

1. **Install `expo-updates`** via `npx expo install expo-updates` (SDK-54-safe).
2. **Create `utils/updateManager.ts`** with `UpdateStatus`, `UpdateManager`, `shouldCheckOnMount`, and `useUpdateManager`, keeping it SDK-agnostic and strictly typed.
3. **Modify `app/index.tsx`** to consume `useUpdateManager`, call `checkForUpdate()` on mount, and render the minimal update banner.
4. **Update `app.json`** with the `updates` block and `runtimeVersion`; add npm scripts to `package.json`.
5. **Run `npx eas-cli init`** to generate `eas.json`; configure `preview` (staging) and `production` channels.
6. **Annotate `.gitignore`** and verify `eas.json` contains no secrets.
7. **Run `npm run lint`** and `npx tsc --noEmit`; fix any flagged issues.
8. **Configure EAS local build** (`eas build --profile preview`) and **publish a staging update** (`eas update --channel staging`); verify on device.
9. **Promote to production** (`eas promote`) and publish the production channel update; verify end-to-end.
10. **Update `README.md`** with the complete OTA publishing runbook and finalize this plan document.
